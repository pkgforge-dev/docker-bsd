## 3. ⛔ The three findings that shape everything next

### 3.1 WHPX presents the HOST hypervisor's identity to the guest

```text
Hypervisor: Origin = "Microsoft Hv"
```

⭐ **Everything else follows from this line.** NetBSD's paravirtual bus looks for
QEMU, does not find it, and never enumerates virtio-mmio, so smolBSD boots a
kernel and never sees a disk. FreeBSD has Hyper-V support and carries on, but
then selects a Hyper-V timecounter it should not trust.

### 3.2 Go binaries misbehave in the guest, and the tidy explanation is WRONG

FreeBSD offers `Hyper-V-TSC(3000) Hyper-V(2000) HPET(950) ACPI-fast(900)
i8254(0) TSC-low(-100)` and picks `Hyper-V-TSC`. Go binaries then die:

```text
SIGFPE: floating-point exception
runtime.deductSweepCredit(0x2000, 0x0)   /usr/local/go125/src/runtime/mgcsweep.go:948
```

`sysctl kern.timecounter.hardware=ACPI-fast` moves `podman run` to `rc=0`.

⛔ **But the clock is NOT the cause.** With `ACPI-fast` selected the clock is
measurably correct: `delta_ns=1002101384` across a one-second sleep. And a
long-running Go daemon then panics the **kernel**:

```text
Fatal trap 12: page fault while in kernel mode
current process        = 1546 (podman)
#5 do_wait+0x123   #6 __umtx_op_wait_uint_private+0x54   #7 sys__umtx_op+0x7e
```

`_umtx_op` is FreeBSD's userspace-mutex syscall and is what Go's scheduler parks
threads on. ⚠ **Something is wrong below the timecounter.** A second kernel page
fault, at `vget_finish` during `rc.shutdown`, happened on another boot that had
run podman; boots that never ran podman shut down cleanly.

### 3.3 The published WHPX CPU-model rule does not reproduce here

⛔ `-cpu host` and `-cpu max` did **not** wedge QEMU on QEMU 11.1.0 on this
host. The sources measured QEMU 9.x on other hardware and are not falsified;
the prediction about this machine is. ⭐ Prefer a named model anyway.

## 6. ⛔ The six defects this session shipped and caught, and the five rules

Five new rows went into ToolKit's `docs/conventions/forbidden-patterns.md`.
⛔ **They must be carried into the standalone repository**, because every one
came from a defect in these very experiments:

1. **A false success.** A marker matched against the guest's **echo of the
   command line that mentioned the marker**. Reported "a container ran" over a
   `podman run` that had errored. ⭐ Fix: make the marker impossible to write
   literally in the command, AND compare with whitespace stripped.
2. **`cmd; rc=$?` under `set -e`** is an unreachable guard. Use `if ! cmd; then`.
3. **A `try`/`catch` around a P/Invoke** cannot tell a missing library from a
   missing entry point. Use `LoadLibrary` then `GetProcAddress`.
4. **A header asserting a property the command line does not enforce.**
   `-display none` says nothing about the network; QEMU attaches a default NIC
   unless given `-nic none`.
5. **Sending a whole line at once to a tty** drops characters.
6. ⚠ Plus two the tables already covered: an exit code read through a pipe
   (`ssh | sed` then `$?`), and a number attributed rather than measured (a boot
   time blamed on `growfs` that had no `growfs` in it).

⚠ **And one more, found twice and not yet written down anywhere:**
`pgrep -f <name>` and `pkill -f <name>` **match their own shell**, because the
pattern appears in that shell's own command line. It produced a false "still
running" report and then a shell that killed itself. Use `-x` and an exact
process name.

## 7. What is open, in priority order

1. ⛔ **Keep a multithreaded Go daemon alive in a FreeBSD guest under WHPX.**
   This is the only thing between here and `podman -c ... run` working. Untried:
   a timecounter chosen for the daemon rather than for a command; setting it at
   boot via `/etc/sysctl.conf` so no Go binary ever runs on `Hyper-V-TSC`;
   FreeBSD's `podman_service` rc script, which exists beside `podman` and was
   never started; a newer or older FreeBSD; fewer vCPUs, since the fault is in
   thread parking.
2. **Cut the 108 s device probe.** A leaner guest, or a machine type with fewer
   devices, is the obvious next measurement.
3. ⚠ **A second host.** Every number here is one machine.
4. ⚠ **Steady-state performance under WHPX was never measured.** Only boot time.
5. **The Hyper-V `.vhd` route** was never built. It needs elevation the WHPX
   route does not.
